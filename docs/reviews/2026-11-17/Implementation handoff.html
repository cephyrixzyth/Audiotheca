First patch in detail · F02 archive keeper protection

Trace. In ArchivePeek.tsx, the control labelled Keep folder explains that the archive can be deleted later. ArchiveDiffWizard.tsx offers the same choice. The API saves "folder" or "archive" keyed by run and path. The staging loop iterates confirmed paths and skips the row when keeper == "folder". The exporter's load_matches() starts instead from CSV verdicts and checks for rejection. It can select a protected archive without consulting its keeper. Its generated script embeds concrete paths, so later changes to the UI cannot edit a previously exported script. Labels · Wizard choice · Preference write · Staging branch · Generated path list

Input state for the current archive and run Expected decision and visible result
Rejected, under any keeper setting Exclude from execution. Show the rejection reason when a row is requested explicitly.
Keep archive, including after a previous confirmation Exclude the archive and its parts. Preserve the extracted copy. Clear or invalidate the stale delete confirmation.
Keep folder, current verified sibling, no delete confirmation Display the preference. A review candidate can remain visible. Live execution still needs explicit approval.
Keep folder, current verified sibling, confirmed Preview lists the archive parts and their destinations. Live moves exactly that set to staging. The extracted folder and its bytes survive.

Next patches for file safety and durable state

F01 · Reverse moves without losing intervening edits

Read guarded_move → log_move → commit_move → _load_entries → rollback_batch, then read execute_history. The committed row currently remembers source, destination and directory status. A path existing at the expected location proves only that something occupies it. A prior successful reversal is also invisible to the current folding logic. Recorded fields · Reversal · Existing success test

First slice. Reject an occupied restore target for files and directories in preview and at execution. Return the conflict per path, leave both contents intact, and make the existing clean round trip pass. Serialize competing operations for the same entries and choose a no-overwrite move primitive appropriate to the filesystem. A separate existence check followed by an overwriting rename still has a race.

Durable slice. Add append-only reversal intent and terminal outcome keyed by original entry and batch. On restart fold them before choosing eligible rows. For an old entry with insufficient identity evidence, recognize a conflict or request manual reconciliation. A duplicate rollback request after success should report zero additional moves. Preserve old committed history. A successful move followed by a failed ledger write is an ambiguous state that needs a new disk check before replay.

Original location Staged location Expected handling on undo
Vacant Matches the recorded object Preview eligibility, reverse once, verify recovered object, record reversal.
Occupied Present Preserve both and report conflict, including if the occupied target is a directory.
Present Vacant Respect a recorded reversal. With only a pending intent, verify identity and reconcile.
Vacant Vacant, or staged identity changed Report missing or changed data. Leave the operation open for review.

Proof. Run the three F01 checks. Then add a two-entry batch with one conflict, retry after resolving it, and reopen the ledger in a second process. Also exercise a cross-device failure and a directory tree where child operations were committed individually. Never infer that every row succeeded from a batch returning ok: true.

F03 · Revalidate a duplicate group at execute time

Read build_plan_from_decisions, add_rejection, the CLI's _cmd_execute, and stage_approved_duplicates. An approval is an earlier statement of intent. The same library may have been edited in the meantime. The planner's initial membership check cannot establish that the keeper still exists at execution time. Saved decision · Rejection persistence · Imported-plan entry · Execution

Patch contract. Validate the current run, library identity, keeper, rejection state and all members before moving any member of that group. Record sufficient identity at approval to distinguish a replacement at the same path. Check the full plan for keeper/other-group overlap, case aliases and directory ancestry. An inexpensive signature may reject a changed file quickly. Where equality justifies a removal, require content evidence appropriate to the whole object. Preserve version-coexist and reference-library decisions as distinct review cases.

State changes. Saving a new choice, clearing a choice or rejecting a group invalidates the old executable revision. At live execute, compare the revision immediately before mutation and record the actual per-member outcome. A group with a missing keeper has zero eligible discards. A failure during the third move retains receipts for the first two and reports the third as unresolved. Replay must consult those receipts.

Proof. Use the provided valid/missing/rejected cases. Add keeper replaced at the same name, keeper inside a discard directory, overlapping groups, old imported plan with missing identity and a single group with two discards where one is unavailable. Run tests/test_duplicate_execute.py and tests/test_duplicate_feedback.py. Check both preview and a live fixture. A 200 response with a count alone cannot establish which copy survived.

F04 · Verify hardlink candidates again when the script runs

Follow the SHA-256 field from build_link_plan into write_hardlink_script. It disappears before the generated function accepts its parameters. Comparing the new link and its keeper after linking compares two names for the same object. A useful negative fixture changes four bytes of the duplicate while leaving its length the same. Plan records · Generated script · Existing test location

Patch contract. Embed the approved digest and verify the keeper plus retained duplicate backup before retiring the backup. Handle an existing backup as a conflict. Verify file identity/link count where supported and restore the original on failure. Never discard the backup when identity or volume capability is uncertain. Concurrent editing during the operation requires an exclusive handle or equivalent protection before removing the last independent copy.

Windows acceptance. Use two initially identical disposable files on a hardlink-capable volume. Generate the plan, change only the duplicate, run the generated script and read both streams back. Repeat with a changed keeper, locked file, pre-existing backup and cross-volume destination. The unchanged pair should share a file ID after success. A text assertion against the generated PowerShell is a useful generator test. It leaves native file behavior unverified.

F05 · Require evidence for the entire folder before unattended staging

The scanner compares up to three ranked files per member. The automatic branch translates a high-confidence MATCH into an action on a whole product folder. Identical filenames, archive bytes, version labels or acoustic similarity can support review with different strengths. Only complete equivalence supports unattended disposal. Sample selection · Automatic decision · Hash selection

Patch sequence. Keep fast candidate generation. Introduce an explicit result for sampled agreement. At the automatic-stage boundary, compare complete relative member paths, file kinds, lengths and full digests. Include empty directories if restoring directory structure is promised. Distinguish unreadable, changed while reading and cancelled from equal. Retain reviewed candidates when verification is expensive.

Proof. Use directories with identical top three payloads and different small presets, extra empty directories, equal contents under different paths, and a member changing during hashing. Record the files and bytes actually compared. For an exact pair, exercise the normal automatic decision with disposable contents and read both the result row and staged tree. A fix may leave the sampler fast when the action gate performs the complete check.

F06 · Give a run a stable identity from CLI launch to browser readback

The producer assigns a minute stamp. The job runner searches recent summary mtimes, the API and report loader use minute-shaped regexes, SQLite clears old rows by stamp, and approvals, exports and URL parameters reuse that stamp. Increasing timestamp precision in just the writer can make a successful scan invisible. Producer · Child correlation · Discovery · Validator · Import replacement

Migration order. Add a type/parser accepting both existing stamps and a strictly specified unique new ID. Introduce one run manifest containing ID, display time, root identity, job ID, completion state and report members. The CLI allocates the ID before writing. API-launched jobs pass the same ID to the child. Return the completed manifest or a machine-readable completion event. Publish the manifest after its files are closed. Use the ID for joins and the timestamp for presentation and chronological ordering.

Compatibility matrix. Old CLI --stamp, old ?run= links, copied Run_Summary_*.txt archives, old decisions, targeted re-import, failed child and no-summary child must all have defined outcomes. Inspect gen_archive_delete_candidates.py and ancillary export scripts for independent regexes. Keep a deliberate import of the same completed run idempotent. Two independently launched scans must never share approvals.

Proof. The supplied test freezes the old producer's clock, completes two normal CLI scans and reads the count through the real API. Add a job-runner test that puts an unrelated recent summary beside the actual child output. Test a missing optional report in the second run and a legacy seeded URL. Record the two IDs, per-run paths, imported row counts and selected run in the browser.

F07 · Put user data in one durable, writable app home

Make an inventory of writable paths before moving any file. Include archive, duplicate, investigation, restructure, scene and vendor feedback, engine hints, exports, engine logging, job store and cache. Several modules calculate path constants when imported. Two one-file processes can load the same source at different extraction paths. The packaging regression is then invisible to a single-process unit test. Home resolver · Feedback location · Engine log · One-file build

Migration order. Prefer the configured home for every new write. Detect an old store and a new store independently. Copy and validate before switching reads, retain the source for recovery, and make repeat migrations idempotent. When two homes have conflicting decisions, preserve provenance, prioritize explicit operator resolution for executable decisions, and keep exports readable. Atomic replacement prevents torn files. Coordinating the full read-modify-write sequence also prevents two reviewers from losing one another's updates.

Proof. Test A → A across two processes, A → B isolation, old-only, new-only, both stores, malformed legacy JSON and read-only install directory. Build the API sidecar, save a keeper, terminate it, restart with the same home and read the same feedback endpoint. The handoff's two-home test exercises the shared-source case. Passing it does not establish frozen restart retention.

F08 · Keep comparison keys separate from execution paths

Store the exact validated original path, operator-visible spelling, root identity and comparison key in a decision record. The current normalized map cannot recover spelling after normalization. Scoped feedback migration also merges legacy keys into later runs. Couple F08 with X05 below before making historical decisions executable. Legacy maps · Keys replayed · Lowercased key · Native execution validation

Migration cases. A v2 key that maps to exactly one member of the bound run can be shown as a recovered suggestion. An ambiguous match, an entry outside the current library or an absent member stays unresolved. Preserve both files on a case-sensitive filesystem where Pack.zip and pack.zip coexist. On Windows, preserve display spelling and resolve equivalence according to the target volume. Moving to another root should trigger a fresh binding.

Proof. Use a mixed-case root, an archive with mixed-case member names, two case-distinct native files on a suitable volume, a legacy slash-normalized Windows record, and a multi-root library. Inspect the actual path sent to the staging function. Simply suppressing a validation error can cause the wrong file to move.
