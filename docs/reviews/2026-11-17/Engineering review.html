Audiotheca engineering review

November 17, 2026 · main at ee8b368 · Engine 10.0.0 · UI/API 1.0.12

Fix the handoff from review to file operations first. A user can choose Keep archive and still see that archive queued for staging. A saved duplicate plan remains executable after its keeper disappears or the user rejects the group. Undo can replace a newer file at the original location. These are separate defects with a common consequence. The operator can make the right decision and still get the wrong filesystem result. Archive staging · Duplicate staging · Rollback

The core workflow is worth preserving. A source CLI dry run on the bundled library produced reports, a second run imported into SQLite, and the API returned the resulting summary. The React production build and all 52 UI unit tests passed. Both Apple Silicon Python sidecars built. The packaged engine completed a dry scan and the packaged API answered its health check. Restarting that API lost a saved archive keeper. The most valuable next release would make that scan → review → execute → undo workflow dependable before adding more tools. Bugs and fixes in priority order

P1 means an incorrect data decision, an unsafe file operation, or lost durable state. P2 means a broken or misleading workflow. P3 means a narrower capability or maintenance issue. Each finding distinguishes observed behavior from consequences inferred by following the source. The acceptance criteria below describe proposed regression tests.

1. P1 · Rollback can overwrite a file created after the move

Observed. I moved an original fixture file using the ledger, then wrote different content at the original path. Undo preview reported one successful reversal. Live undo replaced the newer content with the original. A second preview still reported one reversal after undo had completed. The preview skips collision checks, the live branch passes the occupied destination to shutil.move, and the ledger keeps the entry committed. Directory collisions can also change the effective destination. Undo implementation · Rollback API

Fix. Use the same preflight for preview and execution. Check that the moved object still has the recorded identity and that the restore path is available. Record the actual destination and a terminal reversal state per entry. Preserve both files when the original path is occupied and return a conflict the operator can resolve.

Accept when a new file or directory at the restore path survives untouched, a changed staged file is flagged, a second undo is a no-op, and a partially reversed batch resumes only the remaining eligible entries. Include an interrupted move where the ledger contains a pending operation.

2. P1 · Archive staging reverses the selected keeper

Observed through the review API. On a confirmed archive with a lowercase fixture path, selecting Keep archive returned a successful preview moving the archive to _delete-canidates. Selecting Keep folder returned “keeper preference is extracted folder” and skipped it. The UI labels describe precisely the opposite behavior. Preview and live staging share this branch. Keeper controls · Keeper branch · Saved preference

Exported-plan follow-up. A separately exercised path, gen_archive_delete_candidates.load_matches(), selected a real fixture ZIP after it had been marked keep-archive. Changing only the API condition in a throwaway checkout made two keeper-preview checks pass while the generator check remained red. The executable rows produced by both paths need coverage. Independent candidate generator · Worked first assignment

Fix. Define a decision table for confirmed, rejected, keep-archive, keep-folder and unset states. Selecting keep-archive must invalidate a contradictory archive-delete confirmation. Keep-folder may stage the archive only after an explicit confirmation and verification of the extracted copy. Show the surviving path in both preview and execution results.

Accept when changing the preference after confirmation immediately changes the effective plan, keep-archive always preserves all archive parts, and dry-run and live tests agree for a single archive and a multipart set.

3. P1 · A missing keeper or rejected duplicate group can still be staged

Observed through the review API. After saving a keeper decision, I moved the keeper elsewhere in the fixture. Preview still reported one discard eligible and zero failures. After restoring the keeper and marking the group a bad match, preview gave the same result. The rejection updates feedback and the UI's local selection. Execution reads the previously saved plan and validates only the discard paths. A subsequent live run can remove the only remaining copy from its working location. Discard validation · Rejection handler · Reject and stage controls

Fix. Invalidate the saved approval whenever the group's review changes. At execution, reload the current rejection and verify that the keeper exists, has the expected identity, is distinct from every discard, and remains outside every proposed directory move. Apply the same checks to plans imported through the CLI. Fail the affected group as a unit.

Accept when a missing, replaced, or newly rejected keeper plan moves zero members. An overlapping group that would move another group's keeper must report a conflict before either group changes. Retrying after an interrupted stage must preserve the keeper and reconcile already-moved rows.

4. P1 · Generated hardlink scripts can discard edits made since planning

Source trace. The planner computes a full SHA-256 and stores it in each candidate row. The generated PowerShell function receives only the keeper and duplicate paths. It renames the duplicate to a backup, creates the link, compares the new link's length to the keeper, then removes the backup. Both compared paths already point to the keeper. Nothing verifies that the backup still contains the bytes that were approved. This matters if someone edits a sample between the scan and running the script. Hash-based plan · Generated hardlink operation

Fix. Carry the approved digest into execution. Verify the keeper and the retained original against it immediately before replacing anything. Check device and link identity, preserve the backup on ambiguity, and record a recoverable outcome per row. Exercise the generated script on Windows.

Accept when same-size edits to either file cause a skip and preserve both versions. Also test an existing backup, unsupported hardlinks, a locked file, a cross-volume pair, and interruption between rename and link creation.

5. P1 · Matching three sampled files can stage a different product folder

Observed at the classifier boundary. Two fixture folders shared their three largest files and differed in a fourth. The classifier returned MATCH. It compares up to three ranked files and uses the shortest list across copies. The live engine's automatic mode accepts this result for high-confidence groups and queues the entire other folder. Automatic mode is a configurable path. The default runs in dry-run mode. Content comparison · Automatic staging rule · Default behavior

Fix. Keep the sampled comparison as a cheap candidate filter. Before unattended staging, require a complete manifest of relative path, type, length and full digest for every retained member, with explicit handling of inaccessible or changing files. Report what was compared in the UI.

Accept when extra presets, differing small files, unreadable members, and missing subdirectories all preclude automatic staging. Byte-identical fixture trees should still pass. Compare cold and warm timings on an SMB fixture before enabling full verification broadly.

6. P1 · Two runs in one minute share reports and approvals

Observed end to end. The bundled library produced a four-item run. Immediately scanning a different root produced a two-item run with the same summary path. The API listed one run, SQLite imported two items, and summary readback returned two. The engine uses a minute-resolution stamp and opens report files for writing. Optional files from the first run can coexist with replacement files from the second. Job completion also searches for a recently modified summary instead of receiving the exact run ID from its child. Stamp creation · Report opens · Job-to-summary lookup · SQLite replacement

Fix. Allocate an opaque unique ID before starting the engine, pass it to the child, and store reports and decisions under that ID. Keep a human-readable timestamp for display. Publish a completion manifest after report writes finish. Continue resolving legacy minute-stamped reports and URLs. The API validator and report list regex both require migration. Stamp validation · Legacy report discovery

Accept when two scans with a frozen clock and different roots appear independently in the CLI, API and UI, each imports its own rows, and a failed or partial run cannot inherit another run's approvals or optional CSVs.

7. P1 · Feedback goes to the code directory despite a configured app home

Observed. With AUDIOTHECA_HOME set to a fresh data directory, run reports used that directory. Saving an archive decision wrote feedback beneath the checkout. Changing to a second app home still exposed the first archive confirmation from the shared code directory. Duplicate, scene, investigation and restructure feedback use the same source-relative pattern. Container deployments document the mounted appdata volume as the durable home. PyInstaller one-file processes also have separate extraction directories. I also ran the packaged macOS API twice with the same app home. A fixture keeper was visible immediately after saving on launch one. The feedback endpoint returned an empty keeper map on launch two. Container recreation remains a source-traced risk. Workspace resolution · Archive store · Duplicate store · Appdata contract · One-file packaging

Fix. Resolve writable state through one configurable data-home API. Migrate accessible legacy feedback with a backup and deterministic merge rules, preserve run stamps, and surface permission failures. Move engine logging to the same writable home. Protect read-modify-write operations so simultaneous review actions cannot replace one another.

Accept when two app homes are isolated, two processes sharing a home see the same decisions, a read-only application directory supports normal review, and restarting the packaged API recovers the decisions. Test migrations from existing JSON stores and keep a recoverable copy of the originals.

8. P1 · Archive feedback uses a lowercase comparison key as the actual path

Observed. With mixed case in the configured fixture root, a path accepted by the confirm endpoint was replayed in lowercase. The subsequent staging preview rejected it as outside the configured root. An all-lowercase root reached the keeper logic in finding 2. The stored map discards the original spelling and execution iterates its keys. On a case-sensitive volume, two distinct files differing only by case can also collapse to the same decision. Logical path normalization · Confirmation persistence · Paths returned for execution · Execution path validation

Fix. Store the original, validated, case-preserving path with the run and library identity. Use a separate comparison key that honors the actual filesystem. Resolve older records against the run inventory and require review if reconciliation yields multiple candidates. Preserve existing library-root checks.

Accept when mixed-case Linux/macOS paths round-trip, Windows case variants still resolve appropriately, and an ambiguous legacy record can never select a file for live movement.

9. P2 · Duplicate review drops saved choices beyond group 500 and can retain the previous run's selection

Observed in the API and browser. In a 501-group report, saving the 501st group's valid keeper returned success with a count of zero. The control case for the first group saved one. The plan builder looks up only the first 500 groups and silently skips unmatched keys. The UI requests just 100 groups per filter. In Chromium I selected a keeper in the first demo run and switched to the second. Its feedback response contained zero keepers while the panel still displayed one. The component sets keeper state only when the incoming selection is nonempty. Plan builder · Save response · Run hydration and list request

Fix. Resolve submitted group IDs directly against the complete run. Return explicit saved and rejected keys. Page the list with a stable cursor. Clear run-scoped state, including result panels and counts, immediately when the run changes. Discard late responses for older runs. Support saving an intentionally empty set to revoke the last approval.

Accept when a filtered group beyond 500 survives reload, clearing the last keeper persists, and switching from a run with decisions to one with none shows zero selected. Simulate out-of-order responses while switching runs.

10. P2 · Scan caches can miss nested library changes

Observed at the cache boundary. Editing a file inside a product folder left the enclosing section eligible for cache reuse. The incremental cache uses only the section directory's modification time. The regular per-item cache also uses the product path's modification time. Editing a descendant need not update either directory. The incremental branch additionally sets the section's resolved target list to empty before passing it to coverage-gap detection. Section cache · Per-item cache · Reuse and coverage handoff

Fix. Track file or subtree change evidence, scanner options and identification-rule revisions. On filesystems without a reliable change journal, offer an explicit full verification and display the last fully checked time. Pass previously scanned target paths into coverage accounting on a cache hit. Save the cache atomically.

Accept when nested edits, rename, deletion, changed scan options, and a dropped watcher event all produce correct results relative to a cold full scan. An unchanged repeat scan should report the same coverage and still gain a measurable speed benefit.

11. P2 · Archive diff can hide missing members

Observed at the diff boundary. An archive listing containing instrument-a/kick.wav and instrument-b/kick.wav, compared with one on-disk kick.wav, yielded one matched member, zero archive-only members, and only one archive entry in the output. The join uses basename and setdefault. The disk side lists one directory level. Both inputs are bounded, and the wizard can display a saved scan verdict. This is insufficient evidence to approve a redundant archive. Diff algorithm · Listing and verdict selection · Directory enumeration

Fix. Compare relative member paths and multiplicity recursively. Preserve counts, directory prefixes, truncation and read errors. Use size and CRC or a stronger available digest when appropriate. Present a historical verdict separately from current evidence.

Accept when duplicate basenames, nested folders, a wrapper directory, truncated listings and equal names with changed content produce distinct, intelligible outcomes. Disable a verified-equivalence claim until both inventories are complete.

12. P2 · Long-running jobs can stop delivering new polling events

Observed at the job manager. With retention reduced to three events, the fourth append retained events 1, 2 and 3. Polling after the previously reported total of three returned an empty list. The production default is 8,000. Once the list fills, its length stays fixed, and the scan panel assigns that length to its next polling offset. This affects polled progress and reconnection during a long scan. Retention cap · Cursor slicing · Eviction · Polling cursor

Fix. Assign a monotonically increasing per-job event sequence. Return the oldest available sequence, next cursor and a gap marker when a client falls behind. Use the same cursor semantics for polling and WebSocket replay.

Accept when a small-ring test can cross the retention boundary repeatedly, reconnect, and see terminal completion exactly once. Bound queued data for a slow subscriber and preserve a way to retrieve the durable log.

13. P2 · Dry-run writes report copies inside the scanned library

Observed in both CLI runs. Each writable fixture root acquired a new _dedupe_reports directory and report files. The item movements remained simulated. The CLI help promises “no filesystem changes,” and the dashboard uses equivalent wording. A collector pointing at a shared library can therefore create files there despite selecting preview. CLI help · Library directory creation · Report mirroring

Fix. Write dry-run output to the app home by default. Make report mirroring an explicit destination choice, display it before scanning, and keep the existing underscore-directory exclusion for older libraries.

Accept when the complete library tree and file contents match their pre-scan snapshot after default dry-run, reports still exist in appdata, and explicit mirroring or a read-only share produces a clear result.

14. P2 · Restricted processes raise an unhandled inspection error

Observed in the standard Python suite. test_memory_scan_api and test_mem_scan_unit failed on macOS when psutil.Process(0).memory_info() raised AccessDenied. Only connection enumeration catches permission and zombie errors. Later calls to obtain the name or thread count can also fail if the process exits. Process sampling · API case · Unit case

Fix. Return a structured unavailable or partial result for each inaccessible metric. Make “process gone,” “permission denied,” and a successful sample distinguishable in the API and UI. Add deterministic mocked exceptions and a success test using the test process itself. Keep the native smoke on macOS and Windows.

15. P2 · Browser smoke tests fail on valid tab controls

Observed in Chromium. The main-navigation test timed out waiting for a button named Scan. The run deep-link test selected the expected run, then timed out waiting for a button named Scan audit. Both controls were present with the accessible role tab. In a temporary copy of the tests, changing only the navigation locators to use the tab role made both scenarios pass. CI runs Vitest and the build and omits Playwright. The smoke suite also assumes a specific historical run that exists in the checked-in demo reports. Main navigation test · Deep-link test · CI frontend jobs

Fix. Select tabs by their accessible roles, seed both run fixtures explicitly in an isolated data home, and run Chromium in CI. Keep a second fresh-home case for onboarding. Add one browser workflow that saves a keeper, reloads, previews, changes the decision, then checks the updated result.

16. P2 · The recommended installation paths need release evidence

Verified release discovery and traced Docker startup. The README points first-time users at an installer and names a portable ZIP. The link resolved to the renamed repository's release listing, the public releases API returned an empty list, and the remote had no tags. Separately, the README's all-in-one Docker example omits the proxy secret that the entrypoint requires with its default settings. The entrypoint exits before launching either service. The linked deployment guide does describe the setting. Desktop quick start · Container instructions · Startup precondition · Local build artifact policy

Fix. Make the first install path one that is available. Until installers are published, lead with the verified source path and identify the local package scripts. Derive repository and image owner references from release metadata. Supply a working env-file example for the all-in-one launch. Verify asset names, checksums, image tags and a first-launch scan before announcing a release.

Accept when a clean user can follow the public instructions to an existing asset or build, open the app, scan a sample library and recover a saved review after restart. Verify the exact documented Docker command with a disposable appdata volume.
